# 共享信息约束与管理

本文解释 M1、M2、M3 如何共用账号、空间和占用信息，以及数据由谁写、怎样防止冲突、如何审查变更。当前设计来自 PR #1 的实现草稿；架构和职责仍需小组讨论后确认。

代码中当前如何执行这些约束，见[共享信息约束实现说明](共享信息约束实现说明.md)。

## 1. 共享信息清单

| 信息 | 当前主要记录 | 主要写入者 | 主要读取者 | 管理原则 |
| --- | --- | --- | --- | --- |
| 用户与身份 | `User`、`ApiCredential` | D/账号管理 | 所有业务模块 | 各模块只读取已认证身份；不复制密码或令牌 |
| 角色与权限 | `RoleDefinition`、权限目录 | D/账号管理 | 所有业务模块 | 每个写操作在服务端检查权限；权限码需在目录内 |
| 空间 | `Room` | D/空间管理员 | M1/M2/M3 | 统一空间编号；关闭/注销优先用状态，不随意物理删除 |
| 座位 | `Seat` | D/空间管理员 | M1/M2/M3 | 每个座位只属于一个空间；模块引用统一座位编号 |
| 个人预约 | `Reservation` | M1 | M1/M2/M3、统计 | 保存本人、座位、时段、状态和签到/违约事实 |
| 教室申请与审批 | `ClassroomApplication`、`ApprovalRecord` | M2 | M2/M1、统计 | 每级决定保留审批人、意见和时间；待审批不占用资源 |
| 报修工单 | `WorkOrder` | M3 | M3/M1、统计 | 一个工单指向座位或整室；状态变化按工单号追踪 |
| 资源占用 | M1 使用 `Reservation`；M2/M3 使用 `ResourceHold` | M1、M2、M3 各写自己的业务记录；M2/M3 写公共占用记录 | M1/M2/M3 | 当前 M1 通过预约记录追溯；每条 `ResourceHold` 带模块、资源、时段和来源单号，只由源业务释放 |
| 通知 | `Notification` | 业务模块/worker | 用户本人、worker | 唯一事件键防重复；站内通知不依赖邮件 |
| 审计 | `AuditEvent` | 业务模块/D/worker | 获授权审计人员 | 只记必要操作事实，不记录秘密凭据 |
| 系统参数 | `AppSetting` | D/系统管理员 | 相关业务模块 | 有权限才能修改；记录修改人和时间 |

模型和字段名称以 `backend/campus_app/models.py` 为准。若模型字段与本文不一致，先由负责人确认，再一起更新需求、架构、迁移和测试说明。

## 2. 所有模块共同遵守的不变量

### 2.1 身份与权限

- 每个请求先解析有效账号/令牌，再由服务端权限目录判断操作权限；前端按钮显隐只是辅助。
- 个人预约、申请和报修默认只允许本人读取或取消；跨用户管理权限必须显式授予。
- 部门专属空间除空间管理员外，只向同部门用户开放。
- 屏幕令牌只绑定一个房间，不能拿来登录普通用户；原始令牌不存数据库明文。
- 角色停用或权限撤回后，后续写操作需要重新校验权限。

### 2.2 空间目录

- `Room.id` 和 `Seat.id` 是全系统引用编号；更换显示名称不更换编号。
- 一个座位通过 `room_id` 归属一个空间；空间/座位停用后保留历史关联。
- 新预约和新申请必须重新检查空间/座位是否启用、是否可见和是否处于开放时间。
- 开放时间统一使用本地 `HH:MM` 规则；预约按整点、同一自然日处理，跨日预约目前不支持。

### 2.3 资源占用与冲突

- 时间段使用半开区间 `[开始, 结束)`。若 `A.start < B.end` 且 `A.end > B.start`，两个占用重叠；恰好首尾相接不冲突。
- M1 有效个人预约占一个座位；M2 最终批准占整间空间在批准时段内的全部座位；M3 维修中占被报修座位或整间空间。
- 当前 M1 的事实记录保存在 `Reservation`，M2/M3 的共享占用记录保存在 `ResourceHold`；不能把“统一查询占用”误解为三个模块都直接写同一张表。
- M2 申请只有在最终审批通过时才变成占用；待审批、驳回、超时和取消的申请不应留下有效占用。
- M3 只有进入维修中才下架资源；提交维修完成后仍保持占用，直到验收通过。
- 占用必须记录来源模块和源单号。释放时根据源单号找到自己的记录，不得批量清除其他模块或其他工单的占用。
- 创建占用、更新业务状态、写审计和生成站内通知应在一个事务内完成；若事务失败，不能只留下其中一部分。
- 预约/审批/维修操作需要对同一资源采用一致的并发保护。当前实现使用数据库事务和房间行锁；SQLite 写请求以 `BEGIN IMMEDIATE` 串行化，PostgreSQL 使用行锁处理关键状态写入。

### 2.4 唯一性、历史与通知

- 预约幂等键在同一用户范围唯一；审批记录按申请和审批级别唯一；通知事件键全局唯一。
- 预约取消、超时和维修释放是状态变化，不是删除历史。
- 审计记录至少能指出操作者（或系统任务）、动作、对象类型、对象编号和时间；有需要时记录前后值。
- 邮件发送失败只影响外发渠道，不应撤销已经提交的预约/审批/工单状态。

## 3. 谁能改什么

| 数据类型 | 允许的变更入口 | 不允许的做法 |
| --- | --- | --- |
| User / Role / ApiCredential | D 的认证和管理接口 | M1/M2/M3 私自修改用户权限或读取明文令牌 |
| Room / Seat | D 的空间管理接口 | 业务模块自行维护一套房间列表；直接手改生产数据库 |
| Reservation | M1 的预约/取消/签到流程 | M2 或 M3 直接改 M1 状态绕过 M1 规则 |
| ClassroomApplication / ApprovalRecord | M2 的申请与审批流程 | M1/M3 代替审批人写审批决定 |
| WorkOrder | M3 的报修/派单/维修/验收流程 | M1/M2 直接把工单改为完成 |
| ResourceHold | 由源业务流程创建和释放 | 仅凭座位查询结果手工删除占用；无来源的永久占用 |
| Notification / AuditEvent | 业务事务和 worker | 业务成功后遗漏必要审计；在日志中写密码或令牌 |
| Schema / seed data | Alembic 迁移和幂等种子脚本 | 人工改生产表结构或把演示数据混成业务数据 |

## 4. 接口、事务和架构边界

M1、M2、M3 通过业务接口处理各自的记录；跨模块的资源状态通过统一占用规则解释。PR #1 额外让 M2 终审经 HTTP 调用 D 资源进程，资源进程重新认证用户并在事务内锁申请和空间、检查冲突、写入终审和占用。主 API、资源进程和 worker 当前共用同一代码版本和数据库。

这是 PR 中的架构方案，不等于小组已经决定长期拆分服务。若跨主机传递用户凭据，必须使用 HTTPS 和受控网络；本地/Compose 内的 HTTP 只能留在可信内部网络，资源端口不应暴露给公网。

共享数据库中的表仍有明确写入责任。一个模块不能因为能访问数据库就绕开另一个模块的公开业务流程；附加 Agent 也只能调用公开 API，不直接读写模块表。

## 5. 共享数据变更流程

1. **提出变更**：写明为什么要改、涉及哪些实体/字段/API、受影响的 M1/M2/M3/D 负责人、兼容性和验收场景。
2. **先对契约**：先确定字段含义、编号、状态转换、权限、错误响应和数据迁移办法，再让 AI 或开发者实现。
3. **共同评审**：公共层负责人和所有受影响的模块负责人查看同一 PR；跨模块、RBAC 和 schema 变更必须明确评审意见。
4. **版本化迁移**：修改模型时同步新增/修改 Alembic 迁移和种子脚本；迁移要能从空库重放，并考虑已有业务数据。
5. **行为验证**：针对成功、拒绝、冲突、重试、并发和回滚写可观察的行为测试；不是只检查常量或 mock 掉被测逻辑。
6. **流水线与部署**：PR 自动构建/测试；通过质量门禁后才能合并；测试环境整套部署；生产发布需人工审批、备份、版本标记和回退步骤。
7. **更新记录**：更新需求追踪、架构图、接口说明、决策记录和演示步骤，注明负责人、PR、验证结果和未完成项。

## 6. 当前需特别复核的风险

- **D 的归属及服务边界未定**：`docs/decision-record.md` 的 AD-001 仍待小组讨论。PR #1 将独立资源进程写入项目规则前，应由小组明确它是本次跨模块演示方案，还是长期架构决定。
- **空间/座位状态的并发变更**：预约事务会锁房间来协调 M1 与整室占用；当前管理员停用座位的写路径没有对同一座位加锁。若停用座位与预约同时发生，需进一步审查是否可能提交一笔指向已停用座位的预约，并决定统一锁定策略。
- **邮箱与隐私政策**：SMTP 外发、学校身份认证、个人信息范围和保留期限还未由小组/管理方确认。
- **流水线状态**：PR #1 当前没有显示检查结果或人工 review；报告中的测试数字须与该 PR 的实际提交 SHA 对应后再作为已验证证据。

以上风险应登记为待办，不应被“自动化测试通过”一句话覆盖。
