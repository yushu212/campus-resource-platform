# 校园资源平台共享信息约束实现说明

> 这份说明用通俗语言解释：M1、M2、M3 怎样共用账号、房间、座位和占用信息，系统在什么地方检查权限与冲突，以及目前有哪些边界还要补强。
>
> 本文按仓库当前代码整理，适用于代码阅读和项目汇报。它说明“代码现在怎么做”，不表示所有行为都已由小组正式批准或完成新一轮人工验收。

## 一句话说明

系统不是让每个模块各自维护一份房间清单，而是让大家引用同一套房间和座位编号；每个模块只写自己的业务记录；预约查询会把这些业务记录合起来判断资源是否可用，并返回占用来源。

这里的“共享信息约束”主要靠五件事实现：

1. 一套统一的账号、房间和座位主数据。
2. 每个模块有明确的业务记录写入责任。
3. 服务端权限检查，限制谁能读写哪些记录。
4. 预约、审批和维修流程在写入时检查资源冲突，并用事务和锁保护关键操作。
5. 占用记录保留模块和来源单号，取消或验收时只释放自己的记录。

## 1. 当前系统由哪些部分组成

目前 M1、M2、M3 的业务代码运行在同一套 FastAPI 项目里，共用数据库和模型。M2 最终审批会通过内部 HTTP 请求调用单独启动的 D 资源服务；这个进程和主服务使用同一套代码及数据库。后台 worker 处理提醒和超时任务。

这意味着“共享信息”是由统一的数据表、业务规则和接口实现的；并不是 M1、M2、M3 各自拥有一套独立数据库，也不是每个模块都拆成一个网络服务。

| 部分 | 做什么 | 主要位置 |
| --- | --- | --- |
| D 公共能力 | 账号、角色权限、房间和座位、通知、审计、系统参数 | backend/campus_app/routers/auth.py、shared.py、rbac.py |
| M1 | 搜索座位、个人预约、签到、取消、历史 | backend/campus_app/routers/m1.py、domain.py |
| M2 | 整间教室申请和分级审批；最终审批请求 D 资源服务 | backend/campus_app/routers/m2.py、resource_client.py、resource_service.py |
| M3 | 报修、派单、开始维修、完成、验收和评价 | backend/campus_app/routers/m3.py、domain.py |
| 共享数据模型 | 账号、房间、座位、预约、审批、占用、通知、审计等记录 | backend/campus_app/models.py |
| 数据库结构变更 | 创建和升级表结构 | backend/migrations/ |

## 2. 哪些信息共用，谁负责写

“共用”不代表每个模块都可以改所有记录。当前代码给不同数据明确了写入入口：

| 信息 | 主要记录 | 谁按业务流程写入 | 其他模块怎样使用 |
| --- | --- | --- | --- |
| 用户、角色、凭据 | User、RoleDefinition、ApiCredential | D 账号和权限管理 | 所有模块读取已认证身份和权限，不保存一份自己的用户表。 |
| 房间、座位 | Room、Seat | D 空间管理接口 | M1 查座和预约，M2 申请整室，M3 对具体座位或空间报修。 |
| 个人座位预约 | Reservation | M1 | M1 用来检查时段；M2 终审检查房间是否已有座位预约。 |
| 教室申请和审批 | ClassroomApplication、ApprovalRecord | M2 | M2 推进审批；终审成功后在占用记录中留下 M2 来源。 |
| 物业工单 | WorkOrder | M3 | M3 推进维修状态；开始维修时写占用记录。 |
| 跨模块占用 | ResourceHold | M2、M3 的业务流程 | M1 查询座位时检查；M2 终审和 M3 维修流程也检查相关占用。 |
| 通知、审计 | Notification、AuditEvent | 业务流程和 worker | 用户查看本人通知；获授权的管理人员查审计。 |

要特别记住：**个人预约在 Reservation 表里；M2 和 M3 的占用在 ResourceHold 表里。** 当前产品统一的是“查可用性和追踪来源的规则”，并没有把 M1/M2/M3 的所有记录合并成同一张占用表。

## 3. 系统在哪些地方执行约束

### 3.1 用统一编号指向同一房间和座位

Room.id 和 Seat.id 是跨模块引用的编号。每个座位的 room_id 指向所属房间。预约、申请和工单保存这些编号，因此 M1、M2、M3 指向的是同一份空间主数据。

房间和座位由 D 的管理接口建立或启停。业务模块不各自建立房间清单；修改空间信息通过管理接口完成，表结构变化通过 Alembic 迁移管理。

### 3.2 每次请求在服务端核对身份和权限

请求先由认证依赖解析登录会话或 bearer token，确认凭据有效、用户启用、角色启用。之后业务路由再调用权限目录检查操作权限。部门专属空间还会检查用户部门是否匹配。

例如：

- 学生创建预约需要 reservation:create。
- 学生查看预约时默认只查本人；要看所有预约需要 reservation:read_all。
- 一级审批权限和二级审批权限分开检查。
- 空间目录变更需要 resource:manage。
- 屏幕令牌只允许读取它所属房间的签到码，不能当成普通用户令牌登录。

前端是否显示按钮只是界面体验；真正的限制在后端 API。

### 3.3 在写入时重新检查冲突

用户先搜索到“可用”，不能保证提交时仍然可用。因此 M1 创建预约和 M2 最终审批都会重新查一次资源状态。

时间重叠的判断采用半开区间：两个时段 A 和 B 重叠，当且仅当 A.start < B.end 且 A.end > B.start。比如 10:00–11:00 和 11:00–12:00 首尾相接，不算冲突。

代码入口主要是 domain.py 里的 find_seat_conflict 和 find_room_conflict：

- M1 查一个座位时，检查该座位的有效个人预约，以及覆盖该座位或整间房间的有效 ResourceHold。
- M2 申请整间房时，检查房间里的座位预约，以及覆盖房间或其座位的有效 ResourceHold。
- 查询发现冲突时返回来源模块、来源单号和原因；创建预约遇到冲突时返回冲突响应，不创建预约。
- M3 维修占用的结束时间当前设为很远的上界；维修验收后通过 active=false 释放。查询代码对 M3 占用按“持续有效直到释放”处理。

### 3.4 用事务、行锁和 SQLite 写锁保护关键状态

几个关键写入流程使用数据库事务，避免业务状态、审批结果、占用、通知和审计只写成功一部分。

- SQLite 下，所有非只读 HTTP 请求会先执行 BEGIN IMMEDIATE，先取得写入位置，再读取用于决定是否写入的状态。
- PostgreSQL 下，关键业务流程使用 SELECT … FOR UPDATE 锁住相关申请、工单或房间记录，减少两个请求同时通过检查的机会。
- M1 创建预约会锁房间后再检查冲突和写入 Reservation。
- M2 终审会锁申请和房间，复查开放时间及冲突，再写审批、申请状态和 M2 ResourceHold。
- M3 开始维修会锁工单，并锁相关房间后创建 M3 ResourceHold。
- 同一用户带 Idempotency-Key 重试预约时，会串行检查该用户的请求键，避免网络重试重复创建。

锁和事务能保护已纳入同一锁定约定的写流程；如果另一条管理路径没有采用同一锁，就仍需要补充验证。具体已知风险见第 7 节。

### 3.5 每条跨模块占用都保留来源

ResourceHold 当前保存资源类型、资源编号、模块、来源单号、起止时间、原因和 active 状态。

示例：

- M2 最终批准：module=M2，resource_type=room，source_id=教室申请编号。
- M3 座位维修：module=M3，resource_type=seat，source_id=报修工单编号。
- M3 整室维修：module=M3，resource_type=room，source_id=报修工单编号。

释放时按来源单号定位记录，不会把同一房间里的其他申请、其他工单或个人预约一起清掉：

- M2 取消已批准申请时，释放该申请创建的 M2 占用。
- M3 报修人验收后，释放该工单创建的 M3 占用。
- M1 取消或未签到时，改变自己的 Reservation 状态，不删除历史记录。

### 3.6 用数据库约束和唯一事件键防止重复

除业务路由校验外，数据库模型还有一些结构约束：

- Room.id、Seat.id 等主键确保编号不重复。
- 预约幂等键在同一用户范围唯一；相同键相同内容可返回原预约，相同键不同内容会冲突。
- ApprovalRecord 对“申请编号 + 审批阶段”设唯一约束，避免同一阶段出现两条审批决定。
- Notification.unique_key 设唯一约束，worker 重试时不重复写同一个通知事件。
- 用户、申请、预约、工单和座位之间使用外键关联；取消和验收保留业务历史，不通过删除记录释放资源。

这不是所有业务规则都交给数据库。开放时间、院系访问范围、状态是否允许流转等条件仍由服务端业务代码检查。

## 4. 三条实际数据流

### 4.1 M1：学生预约座位

1. 浏览器向 /api/v1/seats 搜索时段；服务端读取启用的 Room/Seat，过滤用户不能访问的院系空间。
2. M1 查询 Reservation 和 ResourceHold，返回可用状态及已有占用来源。
3. 用户提交预约后，服务端检查预约权限、日期、整点、开放时间、预约时长和座位状态。
4. 服务端锁房间、重新查冲突；没有冲突才创建 Reservation。
5. 预约、审计和站内通知随同一业务请求提交。若有冲突，返回冲突信息，不创建预约。

### 4.2 M2：整间教室审批后占用

1. 申请提交后状态为 pending；这个阶段不创建 ResourceHold，所以不会提前挡住 M1。
2. 一级审批通过后，申请进入第二级审批。
3. 二级审批通过时，主 API 释放本地事务并通过 HTTP PUT 调用内部 D 资源服务。
4. 资源服务重新认证传来的用户凭据，检查终审权限，锁申请和房间，再查房间内的预约及现有占用。
5. 没有冲突时，在一个事务里写第二级 ApprovalRecord、approved 状态、M2 ResourceHold、审计和通知。
6. M1 后续查询读到 M2 来源占用，并显示申请编号；遇到冲突时不应留下“已批准但没占用”或孤立占用。

### 4.3 M3：维修开始时占用座位或整间房

1. 报修时，工单引用一个座位或一个房间；不能同时选两个目标。
2. 派单后，维修人员开始维修；服务端确认工单状态和处理人。
3. 开始维修会把工单改成 in_repair，并创建 module=M3、source_id=工单编号的 ResourceHold。
4. M1 后续搜索会把这条占用作为不可用来源。
5. 维修人员标记完成后，状态为 resolved，但占用仍有效。
6. 报修人或授权管理员验收后，工单改为 accepted，系统只停用这个工单创建的 M3 占用。

## 5. 用一个例子理解“共享但不互相乱改”

假设图书馆 A 房间有座位 A-01：

- 学生甲预约 A-01，M1 在 Reservation 写入预约记录。
- 维修人员开始修 A-01，M3 在 ResourceHold 写入“来源是 WO-工单号”的占用。
- 学生乙搜索 A-01 时，M1 同时查预约和维修占用；如果时段冲突，会返回 M3 的工单号和维修原因。
- 维修人员不能直接删除甲的预约；M1 也不能直接把 M3 工单标记为已验收。
- 维修验收只关闭自己的工单占用。甲的 Reservation 仍按原时间和状态保留。

因此共享的是房间/座位编号和可用性判断；业务记录仍由各模块自己的流程负责。

## 7. 当前实现边界和需要补强的地方

下面这些是代码审查时应讲清楚的边界，不应说成“系统已经完全保证”：

1. **座位停用与预约并发需要补锁。** M1 预约会锁房间，但 /admin/seats/{id}/active 当前直接更新 Seat.active，没有使用同一房间锁或座位行锁。如果恰好与新预约并发，仍需进一步验证是否会出现“座位已停用但预约刚提交”的窗口。
2. **维修开始与已有预约的冲突政策需要明确。** 当前 M3 开始维修会创建维修占用，但这段流程没有调用 find_seat_conflict/find_room_conflict 检查已有预约。它会阻止后续新预约；但对于开始维修前已存在的重叠预约，代码没有在这一步自动取消或拒绝。小组需明确维修能否覆盖已有预约，以及通知/改约怎么处理。
3. **ResourceHold 的源唯一性主要靠业务状态和事务保护。** 当前模型给 ResourceHold 建了查询索引，但没有对“模块 + 来源单号 + 资源”设置数据库唯一约束；重复创建保护依赖工单/申请状态、行锁和业务流程。
4. **不同模块仍有不同记录形态。** M1 用 Reservation；M2/M3 用 ResourceHold。后续若要新增占用来源，必须同步更新查询规则和验收场景。
5. **架构归属仍要小组确认。** M2 的 D 资源进程是当前实现中的内部 HTTP 链路；是否长期单独部署、由谁维护，按决策记录确认。
6. **学校身份、邮箱、数据保留与生产环境未由当前代码决定。** 这些需要管理方或课程小组补充政策。

## 8. 评审时可以这样讲

> “空间和座位只有一份主数据。M1、M2、M3 各自负责自己的预约、审批和工单；M1 查座位时会把个人预约和 M2/M3 的来源占用一起检查。每条共享占用带模块和业务单号，释放时只释放自己的来源。权限在服务端检查，关键写入通过事务和锁保护。当前 M3 开始维修时对已有预约的冲突处理、座位停用并发仍是需要补强的地方。”
